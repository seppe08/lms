## 4. STEP-BY-STEP PLAN

### 4.1 Target project structure (create exactly this)

```
lms/
├── app/
│   ├── __init__.py          # create_app() factory
│   ├── config.py            # Dev / Test / Prod config classes
│   ├── extensions.py        # db, migrate, jwt, etc. (created, not bound)
│   ├── models/              # SQLAlchemy models (DB tables only)
│   │   ├── user.py
│   │   ├── course.py        # Course, Module, Lesson
│   │   ├── enrollment.py    # Enrollment, LessonProgress
│   │   └── mixins.py        # TimestampMixin, SoftDeleteMixin
│   ├── schemas/             # Marshmallow: input validation + output formatting
│   ├── services/            # Business logic
│   ├── api/
│   │   └── v1/              # One blueprint per resource
│   │       ├── auth.py
│   │       ├── users.py
│   │       ├── courses.py
│   │       ├── enrollments.py
│   │       └── progress.py
│   └── common/
│       ├── errors.py        # Custom exceptions + error handlers
│       ├── pagination.py
│       ├── permissions.py   # role_required decorator
│       └── responses.py
├── migrations/              # Generated by Flask-Migrate
├── tests/
│   ├── conftest.py          # app, client, db, auth fixtures
│   ├── factories.py         # Test data builders
│   ├── unit/                # Services, schemas
│   └── integration/         # API endpoint tests
├── wsgi.py                  # Entry point for Gunicorn
├── pyproject.toml           # or requirements.txt
├── .env.example
├── .gitignore
├── Dockerfile
├── docker-compose.yml
└── README.md
```

**Layer flow:** HTTP request → Blueprint route (`api/`) → Schema (`schemas/`) → Service (`services/`) → Model (`models/`).
- Routes are thin: parse the request, call the schema, call the service, return the response.
- Schemas validate input and serialize output.
- Services hold business rules (for example, "can't enroll twice").
- Models handle database access.

**Golden rules (enforce in every phase):**
1. Routes contain no business logic.
2. Services never touch `request` or Flask's `g`, so they stay testable.
3. Models contain no validation of user input. That belongs in schemas.
4. Create extensions in `extensions.py` and initialize them in `create_app()` to avoid circular imports.

**[OPEN ITEM 2]** The plan says `pyproject.toml` "or" `requirements.txt`. Confirm which one to use. Default: `pyproject.toml`, with pinned dependencies.

### 4.2 Technology stack (use these)

| Concern | Choice | Reason |
|---|---|---|
| Framework | Flask + application factory | Simple and flexible; the factory makes testing and config easy |
| Database | PostgreSQL (SQLite for quick local tests only) | Relational data fits LMS relationships, with strong constraints and production-grade reliability |
| ORM | SQLAlchemy 2.x via Flask-SQLAlchemy | Industry standard, with a modern typed style |
| Migrations | Flask-Migrate (Alembic) | Versioned, reviewable, reversible schema changes |
| Validation/serialization | Marshmallow | Declarative, and it separates input from output |
| Auth | Flask-JWT-Extended (access and refresh tokens) | Stateless, good for APIs, with claims for roles |
| Password hashing | `werkzeug.security` or `argon2-cffi` | Never store plain or fast-hashed passwords |
| API docs | flask-smorest | Generates OpenAPI and Swagger UI from blueprints and schemas |
| Testing | pytest + pytest-cov + factory-boy | Fixtures and readable tests |
| Config | `.env` + python-dotenv | Keeps secrets out of code |
| Lint/format | Ruff + Black (or Ruff only), pre-commit | Consistent code, bugs caught early |
| Server | Gunicorn behind Nginx or a platform | Never use Flask's dev server in production |
| Containers | Docker + docker-compose | Same environment everywhere |
| CI | GitHub Actions | Runs tests and lint on every push |

### 4.3 Data model (initial)

```
User ──< Enrollment >── Course ──< Module ──< Lesson
  │                                              │
  └──────────< LessonProgress >──────────────────┘
```

- **User:** id, email (unique), password_hash, full_name, role (`student` | `instructor` | `admin`), is_active, timestamps.

- **Enrollment:** user_id, course_id, enrolled_at, status. Add a **unique constraint** on (user_id, course_id).
- **LessonProgress:** user_id, lesson_id, completed_at. Add a unique constraint on (user_id, lesson_id).

def create_app(config_name="development"):
    app = Flask(__name__)
    app.config.from_object(config_by_name[config_name])

    db.init_app(app)
    migrate.init_app(app, db)
    jwt.init_app(app)

## 6. CONSTRAINTS AND REQUIREMENTS

### Must follow
- Keep the phase order, build order, folder structure, and golden rules in section 4.
- Finish each phase end to end (model → schema → service → route → test) before the next.
- Use these HTTP codes consistently: 201 create, 204 delete, 409 conflict, 422 validation error.
- Use one error format everywhere: `{"error": {"code": "...", "message": "...", "details": {...}}}`.
- Use separate input and output schemas. Never expose `password_hash`.
- Set the role server-side only. Never trust a role sent by the client.
- Check both role **and** ownership in the service layer (to prevent IDOR bugs).
- Enforce unique constraints and foreign keys in the database, not only in app code.
- Use short-lived access tokens plus refresh tokens.
- Commit once per service operation, and roll back on exceptions.
- Paginate every list endpoint and cap `per_page`.
- Use eager loading to avoid N+1 queries.
- Use feature branches, small frequent commits, and pinned dependencies.

### Must not
- Commit `.env` or any secret.
- Install packages globally.
- Put everything in one `app.py`, or create circular imports.
- Hardcode DB URLs or keys.
- Edit the database by hand.
- Edit migrations that have already been applied or shared.
- Trust raw request JSON.
- Store plain-text passwords.
- Leak stack traces in responses.
- Return unbounded lists.
- Use different error shapes per endpoint.
- Write tests that depend on each other or on dev data.
- Test only happy paths.
- Let docs drift from code.
- Use Flask's dev server, `DEBUG=True`, or per-worker migrations in production.
- Build anything listed as out of scope.

### Quality standards
- Autogenerate every migration, **review** it, then commit it.
- Aim for coverage of 80% or more on services.
- Test the permission matrix.
- CI (lint and tests) must pass before you move on.
